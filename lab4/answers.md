## Вопрос 1. Пошаговый сценарий кражи инкремента

Операция `shared_counter += 1` в Python на уровне процессора — это **три шага**:

1. **LOAD** — прочитать значение переменной из ОЗУ в регистр.
2. **INC** — увеличить значение в регистре на 1.
3. **STORE** — записать значение из регистра обратно в ОЗУ.

Между любыми двумя шагами планировщик ОС может сделать **Context Switch** — сохранить состояние текущего потока (включая регистры) и передать управление другому потоку. Если это произойдёт между шагами 1 и 3, один инкремент теряется.

**Пошаговый сценарий:**

Пусть в памяти лежит `shared_counter = 100`.

**Поток 1:**
- Шаг 1 (LOAD): читает `100` из ОЗУ в свой регистр → в регистре `100`.
- **⏸ Context Switch.** Планировщик сохраняет контекст потока 1 (регистр = 100) и передаёт управление потоку 2.

**Поток 2:**
- Шаг 1 (LOAD): читает `100` из ОЗУ в свой регистр → в регистре `100`.
- Шаг 2 (INC): увеличивает → в регистре `101`.
- Шаг 3 (STORE): записывает `101` в ОЗУ. **В памяти теперь `101`.**

**Поток 1 (возобновляется):**
- Восстанавливает свой сохранённый контекст: в регистре по-прежнему `100`.
- Шаг 2 (INC): увеличивает → в регистре `101`.
- Шаг 3 (STORE): записывает `101` в ОЗУ. **В памяти снова `101`.**

**Итог:** оба потока выполнили по одному инкременту (должно было стать `102`), но в памяти осталось `101`. **Один инкремент потерян.**

**Что было в регистрах CPU первого потока, когда таймер прервал его работу:**
В регистре находилось **старое значение `100`** — то самое, которое поток 1 успел прочитать до переключения, но ещё не успел записать обратно.

В нашем эксперименте на Python 3.13 при `STEPS = 1 000 000` гонка не воспроизвелась — итог всегда `2 000 000`. Причина: **GIL** (Global Interpreter Lock) в CPython не отпускается внутри байткодов `+=`, а планировщик Windows переключает потоки слишком редко (раз в ~15 мс), чтобы попасть между LOAD и STORE. Чтобы увидеть гонку, нужен либо больший `STEPS`, либо `sys.setswitchinterval()` с микросекундным значением, либо Python 3.8–3.10, где GIL работает грубее. **Сам этот результат показателен:** он демонстрирует, что GIL в CPython действительно защищает от гонок на коротких операциях.

## Вопрос 2. Решение проблемы через Lock

**Модифицированный код:**

```python
import threading
import time

shared_counter = 0
STEPS = 1000000
lock = threading.Lock()

def worker():
    global shared_counter
    for _ in range(STEPS):
        with lock:
            shared_counter += 1

print("Запуск двух потоков С синхронизацией (Lock)...")
start_time = time.time()

t1 = threading.Thread(target=worker)
t2 = threading.Thread(target=worker)
t1.start()
t2.start()
t1.join()
t2.join()

print(f"Все потоки завершили работу за {time.time() - start_time:.4f} сек.")
print(f"Ожидаемый результат: {STEPS * 2}")
print(f"Фактический результат в памяти ОЗУ: {shared_counter}")
```

**Результаты:**

| | Без Lock | С Lock |
|---|---|---|
| Фактический результат | 2 000 000 | 2 000 000 |
| Время выполнения | ~0.05 сек | ~0.21 сек |
| Разница | 0 | 0 |

**Почему программа с защитой стала работать в несколько раз медленнее?**

`threading.Lock()` — это **мьютекс** (mutual exclusion). Он устроен так:

1. Перед входом в критическую секцию (`with lock:`) поток пытается **захватить** мьютекс.
2. Если мьютекс свободен — поток его захватывает и продолжает работу.
3. Если мьютекс занят другим потоком — текущий поток **блокируется** и ждёт, пока мьютекс освободится.
4. После выхода из критической секции поток **освобождает** мьютекс.

Это значит, что в любой момент времени только **один** поток может выполнять `shared_counter += 1`. Второй поток вынужден **ждать**. То есть **параллелизм исчезает** — потоки выполняются последовательно в критической секции.

Отсюда — замедление примерно в **4 раза** (0.05 → 0.21 сек). Время растёт из-за:

- **Ожидания на мьютексе.** Поток «крутится» в ожидании или переводится в sleep, что занимает время.
- **Системных вызовов.** Захват/освобождение мьютекса — это сисколлы ядра (futex на Linux, критические секции на Windows), а каждый syscall — это переход Ring 3 → Ring 0.
- **Переключений контекста.** Когда поток не может захватить мьютекс, планировщик переключается на другой поток — а это дорогая операция.

При этом сам результат **остаётся точным** — ровно 2 000 000, потому что критическая секция выполняется атомарно: LOAD, INC и STORE не могут быть разорваны другим потоком.

**Итог:** мьютекс — это классический trade-off «точность против скорости». Мы платим производительностью за корректность данных.
